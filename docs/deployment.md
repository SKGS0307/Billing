# Production deployment

The repository is configured for this topology:

```text
Browser -> Vercel frontend and /api reverse proxy -> Render API -> private Render PostgreSQL
```

The browser uses only one public origin. Vercel proxies `/api/*` to Render, so the secure session cookie stays first-party and the API can enforce an exact trusted origin.

## Before deploying

1. Use accounts that have multi-factor authentication enabled on GitHub, Vercel and Render.
2. Protect the GitHub `main` branch and require the `Quality and security checks` workflow.
3. Never commit `.env`, database URLs, admin passwords, API keys or backup files.
4. Choose a permanent Vercel production domain. Preview deployments will not be allowed to mutate production because `APP_URL` accepts one exact origin.
5. Use a paid, persistent Render PostgreSQL plan with managed backups for real store data. The blueprint deliberately does not expose PostgreSQL publicly.

## 1. Deploy the Render API and database

Open:

<https://render.com/deploy?repo=https://github.com/SKGS0307/Billing>

Render reads `render.yaml`. Before creating the Blueprint, provide these secret values when prompted:

- `APP_URL`: the final Vercel production URL, for example `https://billing.example.com`, with no path.
- `SEED_ADMIN_EMAIL`: the real administrator email address.
- `SEED_ADMIN_PASSWORD`: a unique password of at least 12 characters. Do not use the development password.

`AUTH_SECRET` is generated by Render. Do not change it after launch unless all users should be signed out. The pre-deploy command applies migrations and safely seeds foundation roles, permissions and settings. It creates the administrator only when one does not already exist; later deployments do not reset its password.

The expected health URL is:

<https://the-trends-mart-api-skgs0307.onrender.com/api/health>

Do not continue until it returns a JSON response with `status: "ok"` and `database: "connected"`.

## 2. Deploy the Vercel frontend

Import the repository at:

<https://vercel.com/new/clone?repository-url=https%3A%2F%2Fgithub.com%2FSKGS0307%2FBilling&root-directory=frontend>

Use these project settings:

- Framework preset: Vite
- Root directory: `frontend`
- Production branch: `main`
- Build command and output directory: use `frontend/vercel.json`

The API rewrite currently targets `https://the-trends-mart-api-skgs0307.onrender.com`. If Render assigns a different hostname, update that destination in `frontend/vercel.json`, commit and redeploy before testing.

After Vercel assigns the final domain, verify that the Render `APP_URL` exactly matches it. Changing `APP_URL` triggers an API redeploy.

## 3. Acceptance checks

Run these checks on the public Vercel URL:

1. Sign in with the seeded administrator and immediately change the temporary password.
2. Create a category, product and variant; adjust stock; complete and print a test bill.
3. Confirm the sale appears in reports and inventory is reduced exactly once.
4. Confirm Cashier cannot open Users, Settings, Backups or profit reports.
5. Confirm a wrong password is rejected and repeated failures lock the account.
6. Open a deep link such as `/sales`; refreshing it must not show a Vercel 404.
7. Check `/api/health` through the Vercel domain and confirm it is not cached.
8. Enable Render database backups and test a restore into a separate disposable database before launch.

Delete the acceptance-test transactions or replace the empty production database before entering real data.

## Required production values

| Variable | Production value |
|---|---|
| `NODE_ENV` | `production` |
| `APP_URL` | Exact Vercel production origin |
| `AUTH_SECRET` | Render-generated secret |
| `COOKIE_SECURE` | `true` |
| `SERVE_FRONTEND` | `false` |
| `ALLOW_DATABASE_RESTORE` | `false` |
| `DATABASE_URL` | Private Render database connection |

## Operational notes

- All API data is marked `no-store`; HTTPS cookies are HttpOnly, Secure and SameSite Strict.
- The service has global and login-specific rate limits. If it is later scaled to multiple API instances, replace the in-memory limiter with a shared Redis-backed store.
- Application-generated backup files under `/tmp` are temporary. Download them immediately; rely on managed PostgreSQL backups for disaster recovery.
- Run `npm audit`, `npm run typecheck`, `npm run lint`, `npm test` and `npm run build` before each production release. The committed GitHub Actions workflow runs the same quality checks and rejects critical dependency advisories.
